# Require public data properties

GR012 implements the public instance-data policy requested in [issue #82](https://github.com/wkentaro/gruff/issues/82). It pairs direct receiver-store detection with Ruff SLF001 for external backing-field access, because that established companion already catches both reads and writes from a same-module caller of a non-public class. Duplicating it would add a second access policy with different exceptions. A same-class setter makes a public write explicit; a getter alone does not. Internal state only needs an underscore-prefixed name. The rule remains opt-in and offers no autofix because both renaming and introducing a descriptor can change callers' contracts.

The trial recorded on the issue found 74 store sites across 369 Python files at six pinned repository revisions. Eight writes to declared dataclass fields and one inherited standard-library field were concrete compatibility cases. Suppression is chosen over exempting whole decorated classes or subclasses: the latter would also hide ordinary application state in Qt widgets and plugin subclasses. Class-body declarations and generated constructors are outside the source shape, while explicit receiver stores remain subject to the policy. Imported or inherited descriptors, aliases, and runtime rebinding are not inferred. The rule doc records these limits so adoption can be incremental without guessing framework behavior.

## Explicit instance data refinement

[Issue #85](https://github.com/wkentaro/gruff/issues/85) refines the repair guidance and renames GR012 to `explicit-instance-data`, preserving its detection boundaries. Dataclass fields with a generated constructor are preferred for data carriers, including those with small predicates; properties with private backing storage serve behavior, validation, and access control. This replaces the implication that every finding calls for a setter. Explicit writes to declared dataclass fields remain checked, so the guidance distinguishes generated initialization from user-written mutation. Non-public class names still provide no exemption because consumers determine the effective interface. Any independently adoptable rule about classes mixing many fields and substantial behavior must receive a separate code under ADR 0005.
